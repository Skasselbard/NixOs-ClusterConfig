# Package Tooling

`clusterConfig` is a browser/runner for the flake packages generated by
ClusterConfig. It provides Tab completion, descriptions, a tree overview, and a
fuzzy picker so you do not have to remember generated attribute paths.

Every cluster flake exposes it as the default app:

```bash
nix run .# -- list
nix run .#clusterConfig -- list
nix run .#clcli -- list          # shorthand app alias
```

The same derivation is available as a package:

```bash
nix run .#clusterConfig -- show
nix shell .#clusterConfig
clusterConfig list
clcli list
nix profile install .#clusterConfig
```

`clusterConfig` is the canonical binary. `clcli` is a symlink and app alias.

## Commands

```text
clusterConfig list [--flat] [--names-only] [--json]
clusterConfig show [<attr-path>...] [--all] [--json]
clusterConfig path <attr-path>...
clusterConfig run [<path>...] [--dry-run] [--keep-cwd] [-- <args>...]
clusterConfig build [<path>...] [--dry-run] [--keep-cwd] [-- <args>...]
clusterConfig complete [words...]
clusterConfig completions <bash|zsh|fish|nu|install>
clusterConfig index [--names-only]
clusterConfig init [--flake <ref>] [--system <system>] [--force]
```

`list` prints a tree by default:

```text
packages
└── example
    ├── vm0 (machine)
    │   ├── build                 run                  Build the machine configuration locally...
    │   ├── create                run   destructive    Install NixOS on the target host...
    │   └── iso                   build                Build the installation ISO...
    └── secrets (service)
        └── secretEdit            run                  Edit cluster-level secrets
```

`list --flat` prints the same data as an aligned table. `--json` and
`--names-only` are intended for scripts.

`show` without a path prints the flake overview: clusters, machines, VMs,
services, apps, generated `nixosConfigurations`, and the package tree.

`show <attr-path>` prints one package's metadata. If the path is an incomplete
namespace, the CLI prints the available child packages as a hint.

`run` and `build` are aliases for the generated Nix commands:

```text
clusterConfig run example.vm0.deploy
# equivalent to:
(cd <flake-root> && nix run <flake-ref>#example.vm0.deploy --)
```

`run` opens `fzf` when no path is given. `--dry-run` prints the command without
executing it. `--keep-cwd` runs from the caller's directory instead of the flake
root.

Paths can be dotted or split into words:

```bash
clusterConfig show example.vm0.iso
clusterConfig show example vm0 iso
clusterConfig path example vm0 iso
clusterConfig run example.vm0.deploy
clusterConfig run example vm0 deploy
clusterConfig example vm0 deploy        # shorthand for run
```

## Running without `nix run`

The tool is not installed globally by default. Use any of these forms:

```bash
# temporary environment: both clusterConfig and clcli are on PATH
nix shell .#clusterConfig
clusterConfig list
clcli list

# development shell
nix develop .#clusterConfig
clcli list

# persistent install
nix profile install .#clusterConfig
clcli list
```

`nix shell .#clusterConfig` starts an interactive shell. The `-c` form is only
for non-interactive one-off commands:

```bash
nix shell .#clusterConfig -c clcli list
```

The cluster flake also exposes `packages.<system>.clusterConfig` and a
`devShells.<system>.clusterConfig` shell. The framework flake exposes
`packages.<system>.clusterConfig` and `.clcli` as well.

### Installing the CLI on a machine

`clusterConfig` is not part of nixpkgs. To make it available inside a deployed
machine, add the package from the framework flake to the machine's NixOS
modules:

```nix
machines.node1 = {
  nixosModules = [
    {
      environment.systemPackages = [
        clusterConfigFlake.packages.${system}.clusterConfig
      ];
    }
  ];
};
```

Use `inputs.clusterConfigFlake.packages.${pkgs.system}.clusterConfig` if the
module does not already have the framework input in scope. The package contains
both `clusterConfig` and the `clcli` alias. If you reference the cluster flake's
own package output instead, use `self.packages.${pkgs.system}.clusterConfig` and
prefer the framework input when possible to avoid self-referential evaluation.

Legacy `nix-shell` does not consume flake outputs directly. Use the flake-aware
`nix shell`/`nix develop` forms above; a plain `nix-shell` is not supported for
the cluster flake package.

## Working directory

`clusterConfig` never changes the caller's shell directory. Package commands run
inside a subshell that is replaced with `exec`:

```bash
( cd "$flake_root" && exec nix run "$flake_ref#$attrPath" -- "$@" )
```

The executed command sees the flake root as its working directory, which some
helper packages require. The parent shell's `PWD` is unchanged. Use
`--keep-cwd` if a command should run from the caller's directory instead.

## Flake and system resolution

The flake is resolved from:

1. `--flake <ref>`
2. `CLUSTER_CONFIG_FLAKE`
3. `$XDG_CONFIG_HOME/cluster-config/config.json`
4. the nearest parent directory containing `flake.nix`

Global options must appear before the command:

```bash
clusterConfig --flake ./my-cluster list
```

`clusterConfig init` writes the XDG config:

```json
{
  "flake": "/home/user/my-cluster",
  "system": "x86_64-linux",
  "cacheTtlSeconds": 300
}
```

The package system defaults to the flake's `packageSystem` output, so an
`aarch64-linux` deployment-tool system works on an `x86_64-linux` host.


## Package declarations and metadata

Packages carry their metadata in the package declaration:

```nix
extensions.machines.packages.deploy = {
  description = "Deploy the machine configuration";
  action = "run";          # run or build
  destructive = true;
  package = { clusterConfig }: pkgs.writeShellScriptBin "deploy" "...";
};
```

The framework always adds this data to the generated derivation's `meta`:

```nix
meta = {
  description = "...";
  longDescription = "..."; # when set
  clusterConfig = {
    action = "run";
    destructive = true;
  };
};
```

`lib.meta.addMetaAttrs` keeps the derivation's `drvPath` and `outPath`
unchanged, so metadata does not cause a rebuild.

The package index is generated from the declarations without evaluating the
`package` closures. This means packages that recurse when forced, such as an ISO
or a format script, still appear in completion and `list` with their metadata.
Normal Nix inspection also works:

```bash
nix eval .#packages.x86_64-linux.example.vm0.deploy.meta.description
nix eval .#packageIndex.packages
```

Legacy closure-style packages are still accepted:

```nix
extensions.machines.packages.legacy =
  { clusterConfig }: pkgs.writeShellScriptBin "legacy" "...";
```

They appear in the index with generic metadata until migrated. Nested package
namespaces such as `certificates.generate` remain supported.

## Shell completion

Install completion directly:

```bash
clusterConfig completions install          # detects $SHELL
clusterConfig completions install zsh
clusterConfig completions install --shell zsh
clusterConfig completions install --dry-run zsh
```

Default destinations:

| Shell | Destination |
|---|---|
| Bash | `${XDG_DATA_HOME:-$HOME/.local/share}/bash-completion/completions/clusterConfig` |
| Zsh | `${XDG_DATA_HOME:-$HOME/.local/share}/zsh/site-functions/_clusterConfig` |
| Fish | `${XDG_CONFIG_HOME:-$HOME/.config}/fish/completions/clusterConfig.fish` |
| Nushell | `${XDG_CONFIG_HOME:-$HOME/.config}/nushell/clusterConfig.nu` |

The install command creates missing directories and refuses to overwrite an
existing file without `--force`.

For Zsh, add the printed directory to `fpath` before `compinit`:

```zsh
fpath=(~/.local/share/zsh/site-functions $fpath)
autoload -Uz compinit && compinit
```

For Nushell, source the printed file from your config:

```nu
source ~/.config/nushell/clusterConfig.nu
```

The tool package also ships completion files under its standard
`share/bash-completion`, `share/zsh/site-functions`, `share/fish/vendor_completions.d`,
and `share/nushell` directories. `nix profile install .#clusterConfig` can
therefore provide completions without a manual copy; `nix shell` does not update
`fpath` automatically, so use `completions install` there.

To print a script to stdout instead:

```bash
clusterConfig completions bash
clusterConfig completions zsh
clusterConfig completions fish
clusterConfig completions nu
```

The Bash, Zsh, and Fish scripts register both `clusterConfig` and `clcli`.
Completion candidates come from `packageIndex`, so Tab completion stays current
and does not force package derivations.

Top-level completion also offers `clusterConfig` itself. This is intentional:
the CLI is exposed as a normal package with `kind = "tool"` in `packageIndex`, so
it can be inspected or run like any other package (`clusterConfig show
clusterConfig`, `clusterConfig run clusterConfig`). It is not a second command.

## Evaluation model

- **Package index:** generated from declarations; no package closure is forced.
- **Flake overview:** cluster/machine/VM/service names and service roles come
  from the non-forcing overview. It additionally tries a best-effort detailed
  evaluation for fields such as target hosts, system, tags, labels, and selected
  machine services; if a machine definition is self-referential, the basic
  overview is still shown.
- **Derivation meta:** applied lazily when a package itself is evaluated.
- There is no persistent cache yet. `--refresh` and `--no-cache` are accepted for
  forward compatibility.

## Known limitations

- Remote flake references have no local flake root, so `--keep-cwd` semantics
  and helper packages that assume the repository working tree may not work.
- Detailed machine fields are best-effort. A machine whose `targetHost` or other
  fields depend on its own evaluated `nixosConfiguration` cannot be forced
  without recursion; `show` then falls back to names, types, and service roles.
- Bash completion cannot display descriptions.
