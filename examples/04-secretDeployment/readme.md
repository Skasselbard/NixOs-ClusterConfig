# Secret Deployment Example

This example uses the `secret-service` cluster service based on `sops-nix` to install encrypted secrets at NixOS activation time.

## Prerequisites

- A Linux host with Nix and flakes enabled.
- Three VMs that you can deploy to:
  - vm0: `192.168.122.200`
  - vm1: `192.168.122.201`
  - vm2: `192.168.122.202`
- One network interface per VM on the libvirt default NAT network (`virbr0`).
- Host NAT, so the VMs can download packages during deployment. See the
  [Simple Cluster example](../01-simpleCluster/readme.md#host-nat).
- The test SSH private key added to your SSH agent:

  ```bash
  ssh-add ../00-exampleConfigs/secrets/sshKey
  ```

- The deploy helper expects root SSH access to the three addresses above. The
  helpers use `StrictHostKeyChecking=accept-new`, so the first connection trusts
  the host key.

The example age keys and KeePass database under `../00-exampleConfigs/secrets/`
are intentionally public test material. Never reuse them for a real deployment.

## What You Will Learn

- How to declare cluster-scoped, group-scoped and machine-scoped secrets
- How decryption key holders control which machines can read a sops file
- How the service projects declarations into `sops.secrets` and `sops.templates`
- How to edit sops files with the generated helper commands
- How secrets deploy as part of the normal system closure

## Layout

```text
04-secretDeployment/
└── secrets/
    ├── .sops.yaml                 # creation rules generated by the service
    ├── .secret-service-root      # committed root marker
    └── example/
        ├── cluster.yaml           # cluster-wide secrets
        ├── custom.yaml            # custom sopsFile example
        ├── cluster/monitoring.yaml # shared group secrets
        ├── machines/vm0.yaml      # vm0-only secrets
        └── machines/vm1.yaml      # vm1-only secrets
```

`secrets/` is the conventional `./secrets` location relative to this flake. The
service keeps its generated `.sops.yaml` and the root marker inside that root.

## What a decryption key holder is

A sops file has one data key. A **decryption key holder** is a public key whose matching private identity can decrypt that data key. Every value in one sops file shares the same key holders, so the file is the isolation boundary.

`secrets/.sops.yaml` records which key holders apply to which file. sops calls these entries “recipients”.

## Configuration

The cluster service declares the shared group and the cluster-scoped secret:

```nix
services.secrets = {
  selectors = [ filters.clusterMachines ];

  # Helpers may run from any directory inside this flake. The explicit { nixPath; osPath; } form also works.
  sopsRoot = ./secrets;
  machinesSubDir = "machines";
  clusterSubDir = "cluster";

  # Required. The admin key is a key holder for every generated rule and the
  # identity used by the key-holder management commands.
  adminKeySource = {
    type = "age";
    age.sourceKeyFile = "../00-exampleConfigs/secrets/age/admin.key";
  };

  # Secret-group members share one sops file. This is a cluster-local secret
  # group, not an OS group. vm2 is selected by the service but not a member.
  groups.monitoring = [ "vm0" "vm1" ];

  # Explicit custom sops file, relative to sopsRoot.
  secrets.custom.customPassword.sopsFile = "example/custom.yaml";

  # Global cluster secret: no sopsFile means cluster.yaml. Every selected
  # node plus the admin key can decrypt it.
  secrets.cluster.clusterPassword = {
    owner = "root";
  };

  # Group-scoped secret: the sopsFile shorthand selects the monitoring group
  # file, which is readable by its members plus the admin key.
  secrets.monitoring.token = {
    sopsFile = "cluster/monitoring";
    owner = "root";
  };

  # Templates use sops placeholders. The rendered file contains the
  # decrypted value at activation time.
  templates.monitoringEnv = {
    path = "/run/secrets/rendered/monitoring.env";
    content = { config }: ''
      TOKEN=${config.sops.placeholder."example/monitoring/token"}
    '';
  };
};
```

A cluster template can also be limited to a secret group with
`sopsFile = "cluster/<group>"`. Without that marker it is projected to all
selected nodes and must use cluster-wide secrets. Machine templates are still
the right choice for values that only one machine should see.

Machine-scoped secrets live under the machine:

```nix
machines.vm0 = {
  deployment.secrets.keySource = {
    type = "age";
    # A string, not a Nix path, so the private key is not copied into the store.
    age.sourceKeyFile = "../00-exampleConfigs/secrets/age/vm0.key";
  };

  secrets.testService.testSecret = {
    path = "/run/secrets/testService/testSecret";
    mode = "0440";
  };
};
```

### Keepass-escrowed key

vm1 uses the example KeePass database:

```nix
machines.vm1 = {
  deployment.secrets.keySource = {
    type = "keepass";
    keepass = {
      databasePath = "../00-exampleConfigs/secrets/Passwords.kdbx";
      # This example password file lives with the test secrets in 00-exampleConfigs.
      # Real deployments should keep the password outside the repository.
      passwordFile = "../00-exampleConfigs/secrets/keepass.pass";

      # Alternative: read the password from a secret manager or protected command.
      # passwordCommand = "secret-tool lookup service keepass database example";
    };
  };
};
```

The entry password is the vm1 age private key. The public key is derived at runtime; it is not stored in the Nix configuration. `keepass.entry` is optional and defaults to `clusterConfig/<clusterName>/machines/<machineName>`; this example uses `clusterConfig/example/machines/vm1`. `secretsKeyGenerate` creates missing parent groups before writing the entry.

The checked-in `secrets/.secret-service-root` marker identifies this secret root. On a fresh root, create it with:

```bash
nix run .#example.secrets.secretsInitRoot
git add secrets/.secret-service-root
```

Mutating helpers refuse to run until the marker is committed and visible in the evaluated store snapshot.

## Commands

Edit a machine file or set one machine value:

```bash
nix run .#example.vm0.secretEdit
printf '%s\n' 'new-value' | nix run .#example.vm0.secretSet -- --key testService/testSecret
```

Edit the cluster file or set one cluster value:

```bash
nix run .#example.secrets.secretEdit
printf '%s\n' 'new-token' | nix run .#example.secrets.secretSet -- --key monitoring/token
```

Edit or set a value in the monitoring group file:

```bash
nix run .#example.secrets.secretMonitoringEdit
printf '%s\n' 'new-token' | nix run .#example.secrets.secretMonitoringSet -- --key monitoring/token
```

Generate a new key directly in its key source:

```bash
# age source: refuses to overwrite without --force
nix run .#example.vm0.secretsKeyGenerate -- --force

# Keepass source: requires --force to replace an existing entry
nix run .#example.vm1.secretsKeyGenerate -- --force

# Then synchronize recipients and install the new host keys
nix run .#example.secrets.secretsSyncKeyHolders
nix run .#example.vm0.secretsInstallKey
nix run .#example.vm1.secretsInstallKey
```

The public key is derived from the resulting private key and written to `secrets/.sops.yaml` by `secretsSyncKeyHolders`. Do not add public keys to the cluster configuration.

Regenerate `secrets/.sops.yaml` and update the file key holders:

```bash
nix run .#example.secrets.secretsSyncKeyHolders
```

Synchronization only rotates data keys when the generated recipient configuration changed. To rotate all managed data keys unconditionally:

```bash
nix run .#example.secrets.secretsRotate
```

Check the machine and install its key. Deploy the system separately:

```bash
nix run .#example.vm0.secretsCheck
nix run .#example.vm0.secretsInstallKey
nix run .#example.vm0.deploy
```

`secretsInstallKey` installs the age key from `deployment.secrets.keySource`; it does not deploy the system. Use the normal `deploy` command for the system closure.

## Test

After deploying all three VMs, run the user-facing integration test:

```bash
nix shell nixpkgs#age nixpkgs#keepassxc -c bash ./test.sh
```

`test.sh` verifies the deployed result:

- every VM has the expected target key and `0600 root:root` key permissions,
- cluster-wide secrets exist on all selected nodes,
- vm0 and vm1 receive the monitoring secret and rendered templates,
- the group-scoped cluster template is present on vm0/vm1 and absent on vm2,
- vm2 does not receive the monitoring secret or templates,
- the custom `sopsFile` secret exists on all selected nodes,
- machine secrets have the expected owner and mode,
- root can read each secret and `nobody` cannot,
- `secretsCheck` passes for every VM.

The implementation-level helper tests do not need deployed VMs:

```bash
bash ./test-helpers.sh
```

`test-helpers.sh` checks nested-directory invocation and the missing-marker
error. It restores the marker with a trap if a check fails.

### Manual helper checks

These mutate the example sops files. Run them only on a disposable checkout and
review the resulting diff:

```bash
# Set one machine secret from stdin.
printf '%s
' 'new-value' | nix run .#example.vm0.secretSet -- --key testService/testSecret

# Edit a file interactively.
nix run .#example.vm0.secretEdit

# Update recipients or rotate data keys.
nix run .#example.secrets.secretUpdateKeys
nix run .#example.secrets.secretsRotate
```

## Important Notes

- Sops files must be visible to Nix evaluation; for Git-backed flakes, commit them.
- The service does not run Git status checks. Review and commit changes yourself.
- Removing a decryption key holder does not revoke old ciphertext. Run `sops updatekeys`, `sops rotate`, and rotate the actual values.
- Do not commit real age private keys or real secret values. This example uses intentionally public test material.
