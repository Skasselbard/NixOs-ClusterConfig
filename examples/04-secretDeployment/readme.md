# Secret Deployment Example

This example uses the `secret-service` cluster service based on `sops-nix` to install encrypted secrets at NixOS activation time. See the [secret-service user guide](../../src/services/secret-service/Readme.md) for the full command and option reference.

## Prerequisites

- A Linux host with Nix and flakes enabled.
- Three VMs that you can deploy to:
  - vm0: `192.168.122.200`
  - vm1: `192.168.122.201`
  - vm2: `192.168.122.202`
- One network interface per VM on the libvirt default NAT network (`virbr0`).
- Host NAT, so the VMs can download packages during deployment. See the
  [Simple Cluster example](../01-simpleCluster/readme.md#host-nat).
- The test SSH private key added to your SSH agent:

  ```bash
  ssh-add ../00-exampleConfigs/secrets/sshKey
  ```

- The deploy helper expects root SSH access to the three addresses above. The
  helpers use `StrictHostKeyChecking=accept-new`, so the first connection trusts
  the host key.

The example intentionally checks in test keys, a KeePass database and encrypted
sops files, so a fresh checkout is already populated. See
[Initial Setup](#initial-setup) for the clean-start sequence, including
`cleanupSecrets.sh --all`. Never reuse this test material in a real deployment;
real deployments must also commit their encrypted sops files.

## What You Will Learn

- How to declare cluster-scoped, group-scoped and machine-scoped secrets
- How decryption key holders control which machines can read a sops file
- How the service projects declarations into `sops.secrets` and `sops.templates`
- How to deploy and verify secrets, templates and access boundaries
- How to change secret values versus rotating data keys or host identities

## Result

After deployment, the example produces these secrets:

| Scope | Secret | Sops file | Expected key holders | Target | What it demonstrates |
|---|---|---|---|---|---|
| Cluster | `cluster/clusterPassword` | `cluster.yaml` | vm0, vm1, vm2, admin | `/run/secrets/cluster/clusterPassword` (root `0400`) | Cluster-wide access |
| Group | `monitoring/token` | `cluster/monitoring.yaml` | vm0, vm1, admin | `/run/secrets/monitoring/token` (root `0400`) | Group isolation; vm2 is excluded |
| Custom file | `custom/customPassword` | `custom.yaml` | vm0, vm1, vm2, admin | `/run/secrets/custom/customPassword` (root `0400`) | Explicit `sopsFile` support |
| vm0 machine | `testService/testSecret` | `machines/vm0.yaml` | vm0, admin | `/run/secrets/testService/testSecret` (`testService` `0440`) | Machine-private access |
| vm1 machine | `admin/testPassword` | `machines/vm1.yaml` | vm1, admin | `/home/admin/secrets/testPassword` (`admin` `0440`) | Machine-private access with user ownership |

The rendered templates are also part of the result:

- `/run/secrets/rendered/cluster.env` on every VM.
- `/run/secrets/rendered/monitoring.env` on vm0 and vm1.
- `/run/secrets/rendered/monitoring-cluster.env` on vm0 and vm1 only.

The important part is not just which paths exist. vm2 can decrypt the cluster and
custom files while being excluded from the monitoring group file and the vm0/vm1
machine files. That is the isolation boundary demonstrated by this example.

## Layout

```text
04-secretDeployment/
└── secrets/
    ├── .sops.yaml                 # creation rules generated by the service
    ├── .secret-service-root      # committed root marker
    └── example/                   # checked-in encrypted sops files
        ├── cluster.yaml           # cluster-wide secrets
        ├── custom.yaml            # custom sopsFile example
        ├── cluster/monitoring.yaml # shared group secrets
        ├── machines/vm0.yaml      # vm0-only secrets
        ├── machines/vm1.yaml      # vm1-only secrets
        └── machines/vm2.yaml      # empty placeholder; no vm2 secrets
```

`secrets/` is the conventional `./secrets` location relative to this flake. The
service keeps its generated `.sops.yaml` and the root marker inside that root.

## What a decryption key holder is

A sops file has one data key. A **decryption key holder** is a public key whose matching private identity can decrypt that data key. Every value in one sops file shares the same key holders, so the file is the isolation boundary.

`secrets/.sops.yaml` records which key holders apply to which file. sops calls these entries “recipients”.

## Configuration

The cluster service declares the shared group and the cluster-scoped secret:

```nix
services.secrets = {
  selectors = [ filters.clusterMachines ];

  # Helpers may run from any directory inside this flake. The explicit { nixPath; osPath; } form also works.
  sopsRoot = ./secrets;
  machinesSubDir = "machines";
  clusterSubDir = "cluster";

  # Required. The admin key is a key holder for every generated rule and the
  # identity used by the key-holder management commands.
  adminKeySource = {
    type = "age";
    age.sourceKeyFile = "../00-exampleConfigs/secrets/age/admin.key";
  };

  # Secret-group members share one sops file. This is a cluster-local secret
  # group, not an OS group. vm2 is selected by the service but not a member.
  groups.monitoring = [ "vm0" "vm1" ];

  # Explicit custom sops file, relative to sopsRoot.
  secrets.custom.customPassword.sopsFile = "example/custom.yaml";

  # Global cluster secret: no sopsFile means cluster.yaml. Every selected
  # node plus the admin key can decrypt it.
  secrets.cluster.clusterPassword = {
    owner = "root";
  };

  # Group-scoped secret: the sopsFile shorthand selects the monitoring group
  # file, which is readable by its members plus the admin key.
  secrets.monitoring.token = {
    sopsFile = "cluster/monitoring";
    owner = "root";
  };

  # Templates use sops placeholders. The rendered file contains the
  # decrypted value at activation time.
  templates.monitoringEnv = {
    path = "/run/secrets/rendered/monitoring.env";
    content = { config }: ''
      TOKEN=${config.sops.placeholder."example/monitoring/token"}
    '';
  };
};
```

A cluster template can also be limited to a secret group with
`sopsFile = "cluster/<group>"`. Without that marker it is projected to all
selected nodes and must use cluster-wide secrets. Machine templates are still
the right choice for values that only one machine should see.

Machine-scoped secrets live under the machine:

```nix
machines.vm0 = {
  deployment.secrets.keySource = {
    type = "age";
    # A string, not a Nix path, so the private key is not copied into the store.
    age.sourceKeyFile = "../00-exampleConfigs/secrets/age/vm0.key";
  };

  secrets.testService.testSecret = {
    path = "/run/secrets/testService/testSecret";
    mode = "0440";
  };
};
```

### Keepass-escrowed key

vm1 uses the example KeePass database:

```nix
machines.vm1 = {
  deployment.secrets.keySource = {
    type = "keepass";
    keepass = {
      databasePath = "../00-exampleConfigs/secrets/Passwords.kdbx";
      # This example password file lives with the test secrets in 00-exampleConfigs.
      # Real deployments should keep the password outside the repository.
      passwordFile = "../00-exampleConfigs/secrets/keepass.pass";

      # Alternative: read the password from a secret manager or protected command.
      # passwordCommand = "secret-tool lookup service keepass database example";
    };
  };
};
```

The entry password is the vm1 age private key. The public key is derived at runtime; it is not stored in the Nix configuration. `keepass.entry` is optional and defaults to `clusterConfig/<clusterName>/machines/<machineName>`; this example uses `clusterConfig/example/machines/vm1`. `secretsKeyGenerate` creates missing parent groups before writing the entry.

The tracked `secrets/.secret-service-root` marker identifies this secret root.
`secretsInitRoot` creates it together with placeholder sops files when starting
a brand-new sops root. The marker must stay tracked because it is part of the
evaluated-store/working-tree check.

## Initial Setup

This is the complete setup order from a clean checkout. The example intentionally
checks in its keys and encrypted sops files, so a fresh checkout is already
bootstrapped. Reset it before deploying, and only regenerate keys when creating a
new secret root.

### 1. Reset the example

Start from the committed example state and remove local generated files:

```bash
bash ./cleanupSecrets.sh --all
```

This restores the tracked sops files, test keys and KeePass database from `HEAD`,
then removes untracked and ignored build outputs. See
[Reset the example](#reset-the-example) for details.

### 2. Initialize the secret root

Ensure the root marker and any missing placeholder sops files exist:

```bash
nix run .#example.secrets.secretsInitRoot
git add secrets/.secret-service-root
```

The command is safe to repeat. `--force` is only for replacing the root marker.

### 3. Generate initial keys (new secret roots only)

A brand-new secret root with no encrypted values can generate all managed keys:

```bash
nix run .#example.secrets.secretsKeyGenerateAll
```

Skip this step for the checked-in example: its keys already exist and match the
encrypted fixtures. Do not run `secretsKeyGenerateAll --force` against the
example. Replacing every key holder at once leaves no current identity that can
decrypt and re-wrap the existing sops files.

For a new root, run this before adding secret values. To replace one machine key
later, use `<machine>.secretsKeyGenerate -- --force`, then run
`secretsSyncKeyHolders`; the admin key remains available to re-wrap the files.

### 4. Regenerate recipients and re-wrap files

```bash
nix run .#example.secrets.secretsSyncKeyHolders
```

This derives public keys, writes `secrets/.sops.yaml`, runs `sops updatekeys`,
and rotates data keys only when recipients changed. Review and commit any changed
sops files and `.sops.yaml`.

### 5. Install host keys

```bash
./installKeys.sh
```

Or install each key individually:

```bash
nix run .#example.vm0.secretsInstallKey
nix run .#example.vm1.secretsInstallKey
nix run .#example.vm2.secretsInstallKey
```

`secretsInstallKey` installs or repairs the age identity from
`deployment.secrets.keySource`; it does not deploy the system.

### 6. Verify each machine

```bash
nix run .#example.vm0.secretsCheck
nix run .#example.vm1.secretsCheck
nix run .#example.vm2.secretsCheck
```

`secretsCheck` is read-only. It verifies the installed target key, expected key
holders, declared secrets and templates before deployment.

## Deployment

Deploy the three machines:

```bash
./deploy.sh
```

Or run the individual commands:

```bash
nix run .#example.vm0.deploy
nix run .#example.vm1.deploy
nix run .#example.vm2.deploy
```

A normal deploy copies the encrypted sops files as part of the system closure and
activates them on the target.

## Test

After deploying all three VMs, run the automated integration test:

```bash
nix shell nixpkgs#age nixpkgs#keepassxc -c bash ./test.sh
```

`test.sh` verifies the deployed result:

- every VM has the expected target key and `0600 root:root` key permissions,
- cluster-wide secrets exist on all selected nodes,
- vm0 and vm1 receive the monitoring secret and rendered templates,
- the group-scoped cluster template is present on vm0/vm1 and absent on vm2,
- vm2 does not receive the monitoring secret or templates,
- the custom `sopsFile` secret exists on all selected nodes,
- machine secrets have the expected owner and mode,
- root can read each secret and `nobody` cannot,
- `secretsCheck` passes for every VM.

### What to check manually

The test script is the quick regression check. These commands show the
interesting behavior directly.

Run the service's read-only check on every VM:

```bash
nix run .#example.vm0.secretsCheck
nix run .#example.vm1.secretsCheck
nix run .#example.vm2.secretsCheck
```

Inspect target permissions and a rendered template:

```bash
ssh root@192.168.122.200 'stat -c "%a %U:%G %n" \
  /run/secrets/cluster/clusterPassword \
  /run/secrets/monitoring/token \
  /run/secrets/testService/testSecret \
  /run/secrets/rendered/monitoring-cluster.env'

ssh root@192.168.122.200 \
  'cat /run/secrets/rendered/monitoring-cluster.env'
```

You should see the declared owner and mode for each file, and the rendered
template should contain a `TOKEN=` line. Prove the group isolation and access
boundaries:

```bash
# The monitoring secret and group template are absent on vm2.
ssh root@192.168.122.202 'test ! -e /run/secrets/monitoring/token'
ssh root@192.168.122.202 'test ! -e /run/secrets/rendered/monitoring-cluster.env'

# Root can read the secret; an unprivileged user cannot.
ssh root@192.168.122.200 'cat /run/secrets/testService/testSecret >/dev/null'
ssh root@192.168.122.200 \
  'su -s /bin/sh nobody -c "cat /run/secrets/testService/testSecret"'
```

The first two commands should succeed silently. The `nobody` command should
fail with `Permission denied`.

### Helper tests

The implementation-level helper tests do not need deployed VMs:

```bash
bash ./test-helpers.sh
```

`test-helpers.sh` checks nested-directory invocation and the missing-marker
error. It runs `secretsSyncKeyHolders`, which can touch tracked sops files, so
review `git diff` afterward.

### Reset the example

Cleanup and resetting are example-only operations, not part of the normal secret
workflow. Run this before starting a new review so manual experiments do not
carry over:

```bash
bash ./cleanupSecrets.sh
```

This restores tracked sops files, age keys, the KeePass database and test key
material from `HEAD`, and removes untracked generated files under the example
secret roots. To also remove ignored build outputs such as `result`, `build` and
`.direnv`:

```bash
bash ./cleanupSecrets.sh --all
```

The script is intentionally local to this example and is not exposed as a
service package.

## Changing Secrets

Edit a machine file or set one machine value:

```bash
nix run .#example.vm0.secretEdit
printf '%s\n' 'new-value' \
  | nix run .#example.vm0.secretSet -- --key testService/testSecret
```

Edit the cluster file or set one cluster value:

```bash
nix run .#example.secrets.secretEdit
printf '%s\n' 'new-password' \
  | nix run .#example.secrets.secretSet -- --key cluster/clusterPassword
```

Edit or set a value in the monitoring group file:

```bash
nix run .#example.secrets.secretsMonitoringEdit
printf '%s\n' 'new-token' \
  | nix run .#example.secrets.secretsMonitoringSet -- --key monitoring/token
```

`secretEdit` opens the file in `$EDITOR`. `secretSet` reads the value from stdin.
Both change the encrypted value stored in the sops file; they do not rotate the
file's data key. Review the diff, commit the sops file, deploy normally, and run
the checks from [Test](#test).

## Key Rotation and Key Management

These operations are deliberately separate:

- `secretsSyncKeyHolders` regenerates recipients from the current key sources and
  groups. It runs `sops updatekeys` and rotates data keys only when the generated
  recipient configuration changed. Use it after adding or removing a machine or
  changing a key source.
- `secretsRotate` rotates the data key for every managed sops file without
  changing `.sops.yaml`, host identities or logical secret values. Use it for an
  explicit data-key refresh or compromise recovery.
- `secretUpdateKeys` applies the current recipients to the existing data key
  without rotating it. For compromise recovery, follow it with `secretsRotate`.
- `secretSet`/`secretEdit` change the actual secret value; they are not a data-key
  rotation.

Rotate all managed files to try the operation on this disposable example:

```bash
git diff -- secrets
git restore -- secrets
nix run .#example.secrets.secretsRotate
git diff -- secrets
```

The sops metadata and ciphertext change, but the decrypted values do not. If a
key holder was removed because of a possible compromise, update recipients,
rotate data keys, then rotate the actual secret values. Old ciphertext remains
decryptable, so this order matters.

Generate a host key directly in its key source:

```bash
# age source: refuses to overwrite without --force
nix run .#example.vm0.secretsKeyGenerate -- --force

# KeePass source: requires --force to replace an existing entry
nix run .#example.vm1.secretsKeyGenerate -- --force

# Then synchronize recipients, install the new host keys, and deploy
nix run .#example.secrets.secretsSyncKeyHolders
nix run .#example.vm0.secretsInstallKey
nix run .#example.vm1.secretsInstallKey
./deploy.sh
```

The public key is derived from the resulting private key and written to
`secrets/.sops.yaml` by `secretsSyncKeyHolders`. Do not add public keys to the
cluster configuration. `secretsAdminKeyGenerate` replaces the recovery identity
for every generated rule, and `secretsKeyGenerateAll --force` replaces every
managed key, including the admin key. Treat the latter as a bootstrap or
recovery operation, not a routine command.

Do not hand-edit `secrets/.sops.yaml`; `secretsSyncKeyHolders` regenerates it.
Commit it together with the updated sops files. See
[Sync, rotate and key generation](../../src/services/secret-service/Readme.md#sync-rotate-and-key-generation)
and [Rotation and recovery](../../src/services/secret-service/Readme.md#rotation-and-recovery)
for the full operation reference.

## Important Notes

- Sops files must be visible to Nix evaluation; for Git-backed flakes, commit them.
- The service does not run Git status checks. Review and commit changes yourself.
- Removing a decryption key holder does not revoke old ciphertext. Run `sops updatekeys`, `sops rotate`, and rotate the actual values.
- Do not commit real age private keys or real secret values. This example uses intentionally public test material.
